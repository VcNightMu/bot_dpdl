### ⚠️ 警告 1：不要用 `docker compose up` 无差别重建 napcat

**napcat 容器里存着 QQ 登录态**，重建它会导致掉线、必须人工扫码。

而且：napcat 容器标签里的 `config-hash`（`a3f31d77…`）与 compose v2 现在计算的值（`5350aea5…`）**不一致**，
因此**任何不带 `--no-deps` 的 `docker compose up` 都会试图重建 napcat**。

正确做法（本次部署即按此执行）：

```bash
cd ~/bot-dpdl
sudo docker compose up -d --no-deps fastapi     # 只动 fastapi
```

执行后用容器 ID 与启动时间确认 napcat 未被重建：

```bash
docker inspect napcat --format '{{.Id}}|{{.State.StartedAt}}'
```

### ⚠️ 警告 2：`docker-compose`（v1）与 Docker 29 不兼容，已替换

旧版 `/usr/bin/docker-compose`（1.29.2）执行 `up --build` 会在**重建容器阶段崩溃**：

```
KeyError: 'ContainerConfig'      # compose/service.py 读旧镜像元数据
```

后果很严重：它会**先把旧容器改名停掉，然后才崩溃**，导致服务直接中断（本次部署踩到过）。

现已安装 compose v2：

```bash
sudo install -m 0755 docker-compose /usr/libexec/docker/cli-plugins/docker-compose
docker compose version      # Docker Compose version v5.6.0
```

此后请统一用 **`docker compose`**（空格），不要再使用连字符的 `docker-compose`。

### ⚠️ 警告 3：不要把项目里的 `docker-compose.yml` 覆盖到服务器

仓库里那份副本是初版（`napcat/napcat:latest`，拉不到）。
**服务器上那份才是正确的**：镜像用 `mlikiowa/napcat-docker:latest`，多一个 6099 端口，
`WIKI_BASE_URL` 兜底值也已带 `/v1/bot`。

### ⚠️ 警告 4：`.env`、`docker-compose.yml`、`Dockerfile` 都被 `.gitignore` 排除

`git clone`/`git pull` **不会**带来这三个文件。新建服务器时必须手动放置，
否则无法 build（详见 §2.2）。

## 二、部署步骤

### 2.1 上传代码

```bash
# 将项目代码上传到服务器
scp -r bot-dpdl/ root@your-server:/opt/bot-dpdl/
```

### 2.2 配置环境变量

```bash
cd /opt/bot-dpdl
cp .env.example .env
```

`.env.example` 已随仓库提供（2026-10-10 补齐），是环境变量的**权威清单**。
按需填写即可，实际被代码读取的键名如下：

```bash
# NapCat 配置
NAPCAT_HOST=napcat
NAPCAT_PORT=3001
QQ_ACCOUNT=            # 仅 docker-compose 的 napcat 服务使用

# Bot 自身监听
API_HOST=0.0.0.0
API_PORT=8080

# Wiki API（Base URL 必须带 /v1/bot 后缀，漏了会全部 404）
WIKI_BASE_URL=https://wiki.arkrec.com/v1/bot
WIKI_API_TOKEN=你的API Token

# 仅此项目前真正生效
DEFAULT_STALE_DAYS=365

# 以下已定义但【尚未接线到调用点】，改这里不生效：
#   WIKI_MAX_CONCURRENT / WIKI_TIMEOUT_CONNECT / WIKI_TIMEOUT_READ / MAX_MSG_LENGTH
```

> ⚠️ 旧版本本节曾列出 `FASTAPI_PORT`、`DEFAULT_CATEGORY`、`STALE_DAYS` 等键名，
> 这些**在 `config.py` 中并不存在**，填写后不会生效，已按实际实现更正。
>
> ⚠️ 服务器上容器**不挂载 `.env`**，compose 的 `environment` 才是实际来源；
> 用 `docker run` 手工起容器时必须逐个传，尤其不能漏 `WIKI_API_TOKEN`。

### 2.3 启动容器

```bash
docker compose up -d
```

### 2.4 首次登录（扫码）

```bash
# 查看NapCat日志，等待二维码出现
docker logs -f napcat
```

等终端中出现二维码后：

1. 打开手机QQ
2. 点击右上角 `+` → 扫一扫
3. 扫描终端中的二维码
4. 在手机上确认登录
5. 看到日志显示"登录成功"后，按 `Ctrl+C` 退出日志查看

**注意：** 二维码有时效，如果超时了会生成新的，重新扫即可。

### 2.5 验证服务

```bash
# 检查容器状态
docker compose ps

# 检查FastAPI健康检查
curl http://localhost:8080/health

# 检查NapCat是否在线
docker logs napcat | tail -20
```

### 2.6 在群里测试

在QQ群里发送：

```
#help
```

如果Bot回复帮助信息，说明部署成功。

## 三、登录态持久化

### 原理

NapCat的登录凭证（token + 设备信息）保存在容器本地文件系统中。Docker Compose通过挂载卷将这些文件持久化到宿主机：

```yaml
volumes:
  - ./napcat-data:/app/napcat/config
```

这样容器删除重建后，登录凭证仍然存在，NapCat可以用保存的token恢复登录，不用重新扫码。

### Token过期

QQ的登录session有有效期（通常几天到几周），过期后NapCat会掉线。表现是：

- Bot在群里不响应消息
- NapCat日志显示连接断开

**处理方法：**

```bash
# 1. 重启NapCat容器
docker compose restart napcat

# 2. 查看日志，等待新的二维码
docker logs -f napcat

# 3. 手机QQ重新扫码登录
```

### 设备信息绑定

NapCat首次启动会生成 device.json（设备指纹），QQ服务器会绑定这个设备和账号的关系。**必须持久化这个文件**，否则每次容器重启都会生成新设备信息，可能触发QQ安全验证。

持久化目录：`./napcat-data/`（已在 docker-compose.yml 中配置）

#### 更新流程（v1.1 实测可用）

```bash
cd ~/bot-dpdl

# 1. 拉代码（remote 是 ghfast.top 加速镜像，无需凭据）
git pull

# 2. 只重建 fastapi，绝不带 napcat
sudo docker compose up -d --no-deps fastapi

# 3. 验证
curl -s http://127.0.0.1:8080/health          # 期望 {"status":"ok","service":"bot-dpdl"}
sudo docker compose ps                         # 期望两个服务都是 Up
sudo docker inspect napcat --format '{{.Id}}|{{.State.StartedAt}}'   # 确认没被重建
```

`docker compose up -d --no-deps fastapi` 会自动完成「重新 build 镜像 → 重建容器 → 启动」。

#### ⚠️ 本机推送的两个坑（都实际踩过）

**坑 1：代理未运行**。本机 `~/.gitconfig` 里有 `http.proxy=http://127.0.0.1:7897`，
代理客户端没开时 `git push` 直接失败：

```
fatal: unable to access 'https://github.com/...': Failed to connect to github.com:443 over proxy 127.0.0.1
```

实测**绕过代理直连是通的**：

```bash
git -c http.proxy= push origin master
```

**坑 2：不要在非交互环境禁用凭据助手**。本机凭据由 Windows 凭据管理器提供
（`LegacyGeneric:target=git:https://github.com`，user `VcNightMu`）。
为防弹窗挂起应使用：

```bash
GCM_INTERACTIVE=never GCM_GUI_PROMPT=false git push origin master
```

而**不要**用 `-c credential.helper=`——它会连凭据助手一起禁用，报
`could not read Username for 'https://github.com'`，**让人误判成"系统里没有凭据"**（曾因此误诊）。

> 服务器端的 remote 是 `https://ghfast.top/https://github.com/VcNightMu/bot_dpdl.git`，
> 走加速镜像、无需凭据，`git pull` 一直可用。

#### 备用方案：推送不了 GitHub 时用 git bundle

若本地确实无法 `git push`（代理与直连都不通），可绕过远程仓库直接同步提交：

```bash
# 本机：打出一个只含差异的 bundle
git bundle create update.bundle <服务器当前HEAD>..master
git bundle verify update.bundle        # 应显示 "is okay"

# 把 update.bundle 上传到服务器 ~/ 后：
cd ~/bot-dpdl
git fetch ~/update.bundle master
git merge --ff-only <新提交hash>       # 快进，服务器 git 历史保持完整
rm ~/update.bundle
```

比 `tar` 覆盖源码干净：服务器的 `git status` 不会变成一堆"未提交修改"，后续 `git pull` 也不会打架。

## 五、故障排查

| 现象 | 可能原因 | 解决方法 |
|------|----------|----------|
| Bot不响应 | NapCat掉线 | `docker compose restart napcat`，重新扫码 |
| Bot不响应 | FastAPI挂了 | `docker compose restart fastapi`，查看日志 |
| 查询报错 | API Token失效 | 检查 `.env` 中的 `WIKI_API_TOKEN` |
| 查询报错 | IP不在白名单 | 联系wiki管理员添加服务器IP |
| 二维码扫不了 | 二维码过期 | 重新查看日志，会自动生成新的 |
| 登录被拦截 | QQ安全策略 | 换一个QQ号试试 |

## 六、容器内端到端验证方法（v1.1 新增）

只看 `docker logs` 不足以判断"bot 是否按指令回复"——**收到消息也会打 200 OK**，
而非指令消息本就该静默跳过。可靠的验证方式是在容器内直接驱动真实的解析链路：

```bash
# 1. 本机准备探针脚本（内容见下），上传到服务器
# 2. 拷进容器并执行
sudo docker cp e2e_probe.py fastapi:/tmp/e2e_probe.py
sudo docker exec fastapi python /tmp/e2e_probe.py
sudo docker exec fastapi rm -f /tmp/e2e_probe.py
```

探针脚本要点（用**数组格式** payload，模拟 NapCat 的真实推送）：

```python
import asyncio, sys
sys.path.insert(0, "/app")
import config as cfgmod
from api_client import WikiClient
from qq_bot.handler import CommandHandler
from resolver.episode_short import init_episode_short_map
from resolver.operation import build_operation_index

# 与 main.py lifespan 相同的方式构建 operation_index，然后：
h = CommandHandler()
# 关键回归用例：数组格式 + 首尾空格
print(await h.handle([{"type": "text", "data": {"text": "#help "}}], 1, 1, idx))
```

这样能在**真实部署环境**（真实 config、真实 Wiki API）里验证解析与格式化，
而不用等群里有人发指令。

### 判断"指令是否被路由匹配"

```bash
sudo docker logs fastapi 2>&1 | grep '匹配到指令' | tail -20
```

有 `匹配到指令: ^#help$` 这类日志 = 指令被正确识别。

> 注意：bot **发送**消息是通过 NapCat 的 HTTP API 出的，FastAPI 侧**不会**记录，
> 所以日志里看不到"已回复"。要确认回复真的发到群里，只能人工在群里验证。
